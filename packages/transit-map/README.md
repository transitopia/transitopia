# @transitopia/transit-map

The transit engine on a host MapLibre map: the clock, playback, real-time data in the browser, and the WebGL layers that draw vehicles. No UI framework: the site's React controls ([apps/web](../../apps/web/README.md#transit-mode)) read its snapshot store and call its methods. The models it plays back are in [packages/transit-core/DESIGN.md](../transit-core/DESIGN.md).

```ts
const engine = await TransitEngine.create(map, { dataBase, apiBase, theme, config });
const snap = useSyncExternalStore(engine.subscribe, engine.getSnapshot); // in React
engine.toggle(); engine.setRate(10); engine.seek(t); engine.goLive(); engine.select(id);
engine.setTheme("dark");   // before the host swaps the basemap style
engine.dispose();
```

`dataBase` is where the published transit data lives (`var/public/` locally, served at `/dev-data/`; `https://data.transitopia.org/` in production). `apiBase` is the server; without it the engine makes no real-time requests at all and shows schedules only. `region` is the region's id and `config` its settings and feed (`RegionConfig`: kinematics, real time, the feed, and operations and SeaBus where the region has rail and AIS), each checked with `parseConfig` and `parseFeed` (packages/transit-core/src/config.ts): the engine imports no region of its own, so the host chooses (the site's are in `apps/web/src/TransitMap/regions.ts`). It loads the feed's manifest (`data/feeds/<feed>/manifest.json`), and only in a region with rail its tracks, movements, observations and dispatch patches (`data/regions/<id>/`).

## How a frame is drawn

clock → playback → WebGL, every animation frame, without React. Positions are a pure function of (plan, overlays, t), so seeking, rewinding and fast-forwarding cost nothing. Hosts read a small snapshot (`TransitSnapshot` in `engine.ts`: the shown time and service date, play state, the slider's span and the bus coverage within it, the real-time mode, service notices, previews, routes, the selected vehicle, and the datasets drawn), throttled to a few updates a second plus every discrete change.

| File | What |
|---|---|
| `src/engine.ts` | `TransitEngine`: mounts the layers, owns the clock and stores, exposes controls and the snapshot. `debugHandle()` is `window.transit` on `/transit`. |
| `src/clock.ts` | The clock: rate, pause, live, and the playback rates offered (−300× to 300×) |
| `src/plans.ts` | Loads the manifest, the plan for a date's feed, movement files, dispatch patches (static, live and preview versions) and the track network |
| `src/live.ts` | `LivePoller`: polls the live endpoint near now and hands each new response to `rt.ts`, `ais.ts` and the plan store |
| `src/rt.ts` | Real-time buses in the browser: live snapshots near now and recorded hours elsewhere, plus service changes and travel-time profiles |
| `src/ais.ts` | SeaBus AIS: a date's day file continued by the live window, turned into schedule corrections |
| `src/places.ts` | What a station, exchange, stop or route card shows: `placeSnapshot()`, a function of the place, the shown feed and time, the vehicles and the corrections |
| `src/config.ts` | `RegionConfig`: the region's config the host passes to `TransitEngine.create()` |
| `src/url.ts` | Shareable view state in the query string ([below](#url-state)) |
| `src/prefs.ts` | Per-viewer preferences in local storage (theme, hidden routes, legend state), guarded so they work without it |
| `src/layers/` | MapLibre layers ([below](#rendering)) |

## Rendering

- **Vehicles** are drawn by a small WebGL2 layer (`src/layers/gl-polygons.ts`) through MapLibre's public `CustomLayerInterface`. Geometry is built on the CPU (a few hundred to-scale shapes) in frames where something it depends on changed: the time, the zoom, or an input such as new data, the selection or a filter. Paused, that's almost never, so the map isn't repainted every frame; a once-a-second refresh covers what ages with wall-clock time without announcing it (live data going stale). It's built relative to the viewport centre, with the offset folded into the matrix in float64, so positions stay precise at station zoom. Picking is done on the CPU too. This replaced deck.gl, whose MapLibre integration reads private `map.transform` internals that MapLibre v6 removed; keep to the public API.
- **Vehicle shapes** (`src/layers/vehicles.ts`, with the pure geometry in `src/layers/vehicle-geometry.ts`): to scale when zoomed in (trains as chains of car polygons following the track's curvature, buses and vessels as outlines), fixed-size markers when zoomed out. Observed and interpolated positions are solid route colour with a thin darker edge (near-black in the dark theme); **estimated** ones are the route colour at 62% opacity with a white edge, so an estimate never looks observed. The key in the site draws the same two shapes.
- **Track** (`src/layers/tracks.ts`): every SkyTrain track and platform from the infrastructure model. At city zoom parallel tracks merge into one line, wider than any bus corridor. Each main track is drawn west to east with `line-offset`, and of a pair of parallel tracks (within 25 m) each draws its own half of the line, offset so the halves meet at the pair's centreline at every zoom; tracks further apart than the line is wide (twin bored tunnels, island platforms) draw a half-width band each. Where lines share track (Expo and Millennium, Production Way–University to Lougheed) the left track draws the first line's colour and the right one the second's, so the line is split lengthwise. From z15 the line widens to the guideway's true width (9 m) as a ribbon in the line's colour, with the tracks as white hairlines inside. Tunnels and elevated guideway are drawn alike; track is drawn above bus stop ticks (below exchanges, stations and labels), and from z16 to z17 the whole line fades to half opacity and its casing goes, so bus stops and streets under or over the guideway show only close in. Since halves never overlap (and segments end square), the fade is even: MapLibre blends each feature of a translucent layer separately, so overlapping ones would show darker. `?debug=1` adds segment ids, switch and buffer markers, and platform markers.
- **Route lines and stops** (`src/layers/static.ts`): [bus corridors](#bus-corridors) where the plan has them, GTFS shapes for the other buses, SeaBus (the day's berth pair solid, the other dotted) and WCE; bus sections with little or no passenger service dotted; bus stops as ticks toward their side of the street. Hidden routes (by category in the site), "live only" (estimated vehicles not drawn, except the selected one) and hidden stations and stops are per-browser preferences (`src/prefs.ts`). Hiding a route only stops it being drawn: the selected vehicle stays drawn (and computed) whatever its route or provenance, the open route card's route is still computed so its counts stay true, and station and stop cards list every route's departures. Camera follow (`select(id, { follow })`, `setFollowing`) holds the selected vehicle at the centre of the area the host's chrome leaves clear (`setViewPadding`): while following, that area is the map's padding and the vehicle is re-centred every frame the map isn't moving (a `jumpTo` would cancel a gesture), and scroll and pinch zoom go around the centre. A user drag stops it; the padding is then removed without moving the view, once the map is still. Elsewhere ("Centre on map", bringing a tapped place clear of its card) an `easeTo` offset is used instead of padding, so the centre written to the URL stays the map's own. Tapping a station or bus stop selects it instead (`selectPlace`; `?place=`): the snapshot's `place` carries its departures after the shown time, grouped, with frequencies and shared stretches, using the same real-time corrections as the vehicles ([transit-core → Departures](../transit-core/DESIGN.md#departures)), and the map rings it (`setSelectedPlace` in `src/layers/static.ts`). Each departure group also carries its stop ids, the vehicle on the map running its next departure (matched by service date and trip), and where that departure ends (`terminus`: the station or exchange its last stop belongs to, else the stop; absent when that's the place itself), so a card can open them. A card opened from another (`open(target, from)`, where `target` is `{ vehicle }` or `{ place }` and `from` the opening card's title) keeps a trail that `back()` returns along and the snapshot's `back` names; `select` and `selectPlace` (map taps, closing) clear it. Station and stop snapshots list every route stopping there, including catalogue routes the map doesn't draw (`listed` names those; they have no departure groups). Tapping a route line selects the route (`place` of kind `route`: next-hour frequency and its vehicles out; `drawn` is false for a catalogue route, opened from a card or the URL); `routeDays(key)` gives its hourly frequency for each kind of day in the shown feed, cached per feed.
- Layers are re-added after a theme switch: call `engine.setTheme()` before the host swaps the basemap style.
- **Targets**: 60 fps on desktop and ≥ 30 fps on a mid-range phone with ~300 vehicles.

## Bus corridors

Where the plan has [bus corridors](../transit-core/DESIGN.md#bus-corridors), regular bus routes are drawn as one line per street (`corridors` and `corridors-casing` in `src/layers/static.ts`; below z14 the overview corridors, with divided roads as one line), coloured and weighted by frequency tier: every 6 minutes or better dark blue and thickest, every 15 minutes or better lighter blue, every 30 minutes or better purple, less often red and thinnest; nothing without service. Routes with their own colour (the 99 and RapidBus) are drawn along the same corridors, in their colour, a little thicker and cased (`corridors-brand`): each corridor shows the busiest such route running along it at the time shown (feature state `brand`), so they too merge on divided roads below z14 and disappear when they don't run. Where a route runs less than a quarter as often as on its busiest stretch (limited service, such as the 99 east of Commercial–Broadway) it's drawn in the frequency colour instead, its buses counted like any other's; frequency tiers count every route, and the route's colour covers the tier line where it's drawn. Stop ticks follow the same rule. The 99 is orange and every RapidBus the same green, as on TransLink's maps (`config/feeds/translink/routes.json`). Tapping that line opens the route. Bus stops are one tick per stop, in the tier of the buses stopping there (or the route colour where only those routes stop).

Tiers are feature state (`src/layers/bus-frequency.ts`), so the sources are never re-tiled: the engine recounts only when the date, the window (`setBusFrequency("now" | "day" | "night")`, a per-browser preference, the snapshot's `busFrequency`), the hidden routes or the five-minute step of the shown time change. Hidden routes are left out of the counts.

## Real-time data in the browser

- **One live poll**: near "now", `live.ts` polls `/regions/<id>/live/transit` ([apps/server → Live endpoint](../../apps/server/README.md#live-endpoint)) for buses, SeaBus AIS, service changes and live dispatch together (the host passes the region's id as `region`). It waits for the server's `nextAt` plus `clientPollSlackS`, within `clientPollS`–`clientPollMaxS`; the browser revalidates with the ETag, and an unchanged response isn't handed on.
- **Buses**: near "now", `rt.ts` takes the latest snapshot from each live response; at other times it fetches recorded hours from `/rt/history` (the most recently used hours are cached, and only two load at once, so scrubbing across the day doesn't fetch every hour it passes). Positions are predicted between fixes with the learned travel-time profiles ([packages/transit-core/DESIGN.md → Buses](../transit-core/DESIGN.md#buses)). The time slider is shaded where real bus positions exist (`/rt/coverage`), and a badge says whether buses are live, recorded, loading (recorded data covers the time but hasn't arrived yet), estimated, or unavailable. Service changes: while live, the versions the live endpoint points to (immutable files, fetched when the version changes); otherwise the date's current file (`/regions/<id>/days/<date>/translink/changes`), refetched every minute for today and yesterday.
- **SeaBus**: `ais.ts` loads each shown date's day file once, then extends it with the live endpoint's AIS window; a window that doesn't reach back to what it has (the tab slept) refetches the day file, as does a date in progress without live data (every `clientPollMaxS`). It runs the AIS matcher on the fixes and passes `ScheduleCorrections` to the schedule engine ([→ SeaBus AIS](../transit-core/DESIGN.md#seabus-ais)).
- **SkyTrain**: the engine never reconciles rail observations itself. It loads the date's dispatch patch: the live version the live endpoint points to, else the static one published with the build, else the base plan.
- **Timetable vehicles** with manual observations use `reconcileScheduled()` (merged with AIS corrections; manual ones win).
- If the server is down or `apiBase` isn't set, everything falls back to the static build, marked *estimated*.

## URL state

The query string holds the transit mode's state: `?date=2026-09-28&t=08:15:00&rate=10&paused=1&select=<vehicle>` (`v` is the older name for `select`), `scenario=<name>`, and `preview=<YYYYMMDD>:<version>,…` for unconfirmed corrections. No time parameters means live. `t` is service-day time, so it may exceed 24:00 for after-midnight trips. The map position is in the hash, shared with the other modes ([apps/web](../../apps/web/README.md#modes-and-url-state)).
